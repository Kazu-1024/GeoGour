# 簡易仕様書

## アプリ名：Geoグル（GeoGour）

現在地から近い飲食店を探せるグルメ検索Webアプリです。  
位置情報を起点に検索することで、「今いる場所からすぐ行けるお店」を見つけられる体験を目指しました。

## 機能概要（機能一覧）

### 1. 店舗検索機能
現在地または条件を指定して、周辺の飲食店を検索します。
- **現在地取得検索**: ブラウザのGeolocation APIを利用し、現在地付近のお店を一発検索。
- **条件絞り込み**:
  - **検索範囲**: 5段階（300m〜3000m）から選択。
  - **ジャンル指定**: 定番ジャンル（居酒屋、焼肉、カフェ等）でフィルタリング。

### 2. 店舗詳細表示機能
店舗の詳しい情報を確認できます。
- **基本情報**: 住所、営業時間、定休日、予算目安、アクセスなど。
- **サービス情報**: 飲み放題・食べ放題の有無、カード利用可否をバッジで見やすく表示。
- **地図**: Google Mapsによる位置表示。
- **外部予約**: ホットペッパーグルメ公式ページへ遷移し、予約が可能。

### 3. 閲覧履歴機能
過去に気になったお店へ素早くアクセスできます。
- **履歴保存**: 詳細ページを見た店舗を自動保存（LocalStorage利用）。
- **自動整理**: 最大10件まで保持し、30日経過した古い履歴は自動的に削除。

## テーブル定義(ER図)などの設計ドキュメント

現在はホットペッパーAPIからのデータ取得を主としていますが、将来的な「お気に入り機能」や「ユーザー設定」の実装を見据え、以下のデータベース設計を行っています。
（Docker環境には PostgreSQL 16 を構築済み）

### 予定しているER構成

#### 1. users テーブル
ユーザー認証・基本情報を管理します。パスワードはセキュリティを考慮し、生の文字列ではなくハッシュ値として保存する設計です。

| カラム名 | データ型 | 制約 | 説明 |
| :--- | :--- | :--- | :--- |
| id | UUID | PK | ユーザーID |
| name | VARCHAR(255) | NOT NULL | ユーザー表示名 |
| email | VARCHAR(255) | UNIQUE, NOT NULL | メールアドレス（ログインID） |
| password_hash | VARCHAR(255) | NOT NULL | パスワード（ハッシュ値） |
| created_at | TIMESTAMP | DEFAULT NOW() | アカウント作成日時 |
| updated_at | TIMESTAMP | DEFAULT NOW() | 最終更新日時 |

#### 2. favorites テーブル
ユーザーのお気に入り店舗を管理します。同一ユーザーによる同一店舗の重複登録を防ぐため、複合ユニーク制約を設定します。

| カラム名 | データ型 | 制約 | 説明 |
| :--- | :--- | :--- | :--- |
| id | UUID | PK | お気に入りID |
| user_id | UUID | FK | ユーザーID（users.id参照） |
| shop_id | VARCHAR(50) | NOT NULL | ホットペッパー店舗ID |
| note | TEXT | | ユーザー用メモ（任意） |
| created_at | TIMESTAMP | DEFAULT NOW() | 追加日時 |

**※制約事項**: `(user_id, shop_id)` の組み合わせに対して UNIQUE 制約を設定し、整合性を保つ予定です。

## 開発環境構築手順

Dockerを利用してローカル環境で動作させる手順です。

### 1. リポジトリのクローン

```bash
git clone https://github.com/kazu-1024/GeoGour.git
cd GeoGour
```


### 2. 環境変数の設定
`.env.example` をコピーして `.env` を作成し、必要なAPIキーを設定します。

```bash
cp .env.example .env
```
※ `HOTPEPPER_API_KEY` には有効なAPIキーを設定してください。

### 3. アプリケーションの起動
Docker Composeを使用してコンテナをビルド・起動します。

```bash
docker compose up --build
```

### 4. 動作確認
起動完了後、ブラウザで以下にアクセスしてください。
- Frontend: http://localhost:5173

## コンセプト
**「ここから、すぐ行ける。」**
複雑な検索条件を入力する手間を省き、位置情報を活用することで、移動中でもサッと周辺のお店を探せる**「現在地特化型」**のグルメ検索をコンセプトにしました。

## こだわったポイント

### 1. ホットペッパーAPIへの最適化された導線
仕様上から「アプリ内ですべて完結させる」のではなく、「検索と選定まではアプリで高速に行い、予約や詳細確認は公式（ホットペッパー）へスムーズに送客する」という役割分担を明確に設計しました。

### 2. 拡張性と保守性を意識したアーキテクチャ (BFF的な役割)
Frontend専用のBackend（BFF: Backend For Frontend）を配置することで、ホットペッパーAPIの仕様変更や複雑さを吸収する設計にしました。
- **パラメータ拡張への強さ**: 将来的に表示項目を増やしたい場合でも、Backendの構造体 (`struct`) とFrontendの型定義 (`type`) を追加するだけで安全に対応できる構成にしています。
- **責務の分離**: 外部APIとの通信ロジックを `internal/client` に集約し、Handlerやエラー処理と切り離すことで、メンテナンス性を高めました。

### 3. モバイル対応・レスポンシブデザイン（を目指して）
「移動中に使う」ユースケースを想定し、スマートフォンでの操作を想定し、実装することを目指しました。
- Tailwind CSSを用い、PC/タブレット/スマホそれぞれの画面サイズで見やすくなるよう調整を行いましたが、最適なUX設計にはまだ課題が残ると感じています。

### 4. デプロイを見据えたコンテナ環境
開発環境（`docker-compose` + `Air`）を構築し、環境変数を `.env` に分離することで、本番環境への移行を意識した構成にしています。
- ただし、現状のDockerfileは開発用のシンプルな構成のため、本番向けの最適化（マルチステージビルド等）は今後の課題です。

## デザイン面でこだわったポイント
- **「情報を詰め込みすぎない」**: ユーザーが知りたい情報（写真、店名、ジャンル）に絞って表示し、認知負荷を下げました。
- **視覚的なステータス表示**: 「飲み放題」「カード可」などの条件は、文字だけでなく色付きのバッジで直感的に分かるようにデザインしました。

---

## 技術面でアドバイスして欲しいポイント
- **閲覧履歴のベストプラクティス**: 現在は手軽さを優先して `LocalStorage` でID管理を行っていますが、CookieやIndexedDB、あるいはDB管理と比較して、実務ではどの手法が選択されることが多いか。
- **エラーハンドリングの設計**: 現在は外部APIや通信失敗時に最低限のエラー分岐を行っていますが、エラーの種類ごとにどこまで責務を分けるべきか（BFFで吸収すべきか、フロントで表現すべきか）については、より良い設計があると感じています。実務ではどの程度までエラーを構造化し、UIに反映するのが一般的なのかを学びたいです。
- **フォルダ構成の妥当性**: 今回はフォルダ構成も意識して制作していこうと考えていました。Frontendに `{components,pages,hooks,contexts,types,constants}`、Backendに `internal/{handler,client,errors,config,model}` という構成を採用しましたが、この規模のアプリに対して適切だったのか、あるいは別の構成がより良かったのではないか、という点についてご意見をいただきたいです。

## 自己評価
- **できたこと**: 「現在地から探す」というコア機能を一通り実装し、Dockerでの開発環境構築まで完了できました。特に、バックエンドをBFFとして介在させることで、フロントエンドのロジックをシンプルに保てた点は良かったと感じています。
- **課題・反省点**:
    - **デプロイ未達**: 本番環境へのデプロイを目標にしていましたが、環境構築の設定に手間取り、ローカル動作までの確認で時間切れとなってしまいました。
    - **デザインとUX**: レスポンシブ対応や配色は「それっぽく」なりましたが、ユーザー体験を突き詰めた設計には至らず、デザインの難しさを痛感しました。
    - **デバッグ効率**: 開発終盤で発生した単純なエラー（変数の渡し間違い等）の特定に多くの時間を費やしてしまいました。気をつけて実装していかないといけないログ出力やデバッグ手法の引き出しを増やす必要性を感じています。

## 今後の展望・修正案

### 1. デプロイ環境への挑戦
今回は開発環境の構築と機能実装に注力したため、やりたかった本番環境へのデプロイまでは到達できませんでした。
今後は、Render.com や AWS App Runner などのサービスを調査し、「公開するとしたらどう設計すべきか」という視点でデプロイにも取り組んでみたいと考えています。
実際に第三者に触ってもらうことで、設計やUXの課題をより明確にしたいと感じました。

### 2. デザインプロセスの見直し
実装を優先するあまり、デザインを後追いで調整する形になってしまいました。
その結果、レスポンシブ対応や情報の出し方に迷う場面が多く、設計段階での検討不足を感じました。
次回は、簡単なワイヤーフレームを作成した上で実装に入るなど、デザインと実装の関係を意識した進め方を試してみたいです。

### 3. DB連携（お気に入り機能）の検討
今回は外部APIを利用した検索体験にフォーカスしましたが、アプリとしての継続的な価値を考えると、ユーザーごとの状態を持つ仕組みも必要だと感じました。
将来的には、認証機能やお気に入り保存などを実装した場合の設計を検討し、「検索特化のアプリ」から一歩踏み込んだ構成も考えてみたいと考えています。
